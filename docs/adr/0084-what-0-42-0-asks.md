# ADR 0084: What guideline 0.42.0 asks

**Status**: accepted (2026-09-30).

## Context

Tadas moves its pin from guideline v0.41.0 to v0.42.0, by a merge of
its `scaffold` branch. The branch holds the guideline's scaffold
rendered as `tadas`, at v0.41.0 and then at v0.42.0, so the merge
brings in only what the scaffold changed between the two.

The release changes no section of the guideline, no lens, and no rule
the checker holds, and it reverses nothing. It changes the scaffold's
two operational skills, `ops-watch` and `ops-investigate`, and the
tests that hold them. Here is where Tadas stands on each change:

| What v0.42.0 changes | Why | Here |
|----------------------|-----|------|
| `ops-investigate` step 4 searches the schema the app's series carry, with `OTelLib`. | The exporter adds `OTelLib` to every series. A `SEARCH` whose schema leaves a dimension out matches nothing and answers with no error, so the request query read zero. | Taken. It read zero on a deployed Tadas too. The dashboard module writes the same two schemas. |
| Each skill gives the cloud call of every signal it reports: the requests, the counts by status and route, the p95, the outcomes, and the database's connections. | A step that names a signal and no call leaves the call to whoever runs it. | Taken. The load balancer and the database are named `tadas-<env>` here, as the calls write them. |
| The cloud p95 is the load balancer's: one number for every route together, in milliseconds, or `none`. | The app's histogram reaches CloudWatch as a statistic set, which holds no percentile. | Taken. |
| A watch batch whose cloud `requests` is 0 writes "metrics not read". | The load balancer's health checks are requests, so a zero is a read of nothing. | Taken. |
| `ops-investigate` step 6 asks Sentry's own host for its window as `lastSeen:-<since>`, and sends no `statsPeriod`. | The tracker takes `statsPeriod` only as `24h` or `14d`, and answered the default hour with a 400. GlitchTip reads `lastSeen:` as a tag no issue carries. | Taken. |
| `infra/tests/test_ops_skills.py` holds every `SEARCH` schema the two skills write to the ones the dashboard module writes. | A schema that drifts from the series fails in silence. | Taken, with no line of Tadas's own. |

`make check` runs `arch-check` at v0.42.0, and it passes: 106 rules over
356 files, no finding, and 7 accepted by an exception. The same five
entries of `[[tool.arch-check.exception]]` accept them as at v0.41.0.

## Decision

**The move is a merge of the scaffold.** The pull request that carries
it merges with a merge commit, never a squash, so the render it merged
stays the base of the next move.

**Tadas takes the release whole.** Every line the scaffold changed is
in the two skills and their tests as the scaffold wrote it. One
sentence of `ops-investigate` step 5 takes both sides: the scaffold's
"as above", which points at the new call, and Tadas's "each queue",
since it has two.

**What stays different is Tadas's.** In the two skills that is its
product: the second queue, the payment processor and Slack beside the
identity provider, the kinds of its orchestrations, and the tasks in
the size line. The tests differ in nothing.

**Nothing of v0.42.0 is a deviation.** The deviations table is as it
was.

## Consequences

- The next pin move merges the `scaffold` branch again, from the
  v0.42.0 render.
- An investigation or a watch of a deployed environment reads its
  requests, its error ratio, and its outcomes from CloudWatch by the
  dashboard's schemas. Its p95 is one number, never one per route.
- A schema that changes in the dashboard module changes in the two
  skills with it, or `infra/tests/test_ops_skills.py` fails.
